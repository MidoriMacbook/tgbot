## Назначение

Единый работающий прототип приёма и обработки заявок: пользователь обращается к исполнителю через мессенджер, заявка поступает в единую БД и обрабатывается сотрудниками через веб-интерфейс. Заявитель отслеживает прохождение заявки и получает уведомления о статусе. Установка дополнительного приложения заявителю не требуется.

Платформа из ТЗ — MAX; Telegram разрешён как альтернативный вариант для демонстрации. Возможные сценарии: ремонт классов и оборудования школы, услуги управляющей компании, техническая поддержка мероприятия.

## Термины

- Классификатор — справочник категорий заявок, состоящий из групп и элементов.
- Заявка, или тикет, — обращение с обязательным номером, категорией, описанием и статусом.
- Оператор — сотрудник, обрабатывающий заявки через веб-приложение.
- Админ-панель — раздел управления классификаторами, сотрудниками и заявками.

## Обязательные функциональные требования

### Бот

| Код | Требование и критерий приёмки |
| --- | --- |
| B01 | Бот приветствует пользователя и описывает работу системы. |
| B02 | Пошаговая подача: выбор группы → выбор элемента → описание проблемы → контакт для обратной связи. |
| B03 | Не менее трёх групп классификатора, не менее трёх элементов в каждой; при смене тематики сохраняется структура 3 × 3. |
| B04 | Каждой заявке присваивается уникальный номер; данные сохраняются в БД. |
| B05 | Статус можно запросить по номеру заявки в любой момент. |
| B06 | Незаполненные поля не принимаются; действие «назад» доступно на каждом этапе подачи. |

Начальное наполнение из примера в ТЗ:

| Группа | Элементы |
| --- | --- |
| Оборудование | Проектор, принтер, компьютерный класс |
| Помещение | Кабинет, коридор, столовая |
| Обслуживание | Wi-Fi, электрика, мебель |

### Веб-приложение

| Код | Требование и критерий приёмки |
| --- | --- |
| W01 | Авторизация сотрудников; предусмотрены роли оператора и администратора. |
| W02 | Лента всех заявок с фильтрами по статусу, группе классификатора, исполнителю и дате. |
| W03 | Жизненный цикл со статусами «Новая» → «В работе» → «Выполнена» / «Отклонена». |
| W04 | Оператор может взять заявку в работу. |
| W05 | Оператор может назначить заявку сотруднику. |
| W06 | Оператор может переназначить заявку другому сотруднику; история сохраняется. |
| W07 | Закрытие заявки требует обязательного комментария о результате. |
| W08 | Карточка содержит номер, дату, категорию, текст, заявителя, текущего исполнителя и полную историю изменений. |
| W09 | Администратору доступны справочники классификаторов и список сотрудников. |
| W10 | Администратору доступна статистика количества заявок по статусам и категориям. |

### Интеграция и уведомления

Раздел 3.3 исходного ТЗ обозначен как дополнительное требование, дающее плюс к оценке.

| Код | Требование и критерий приёмки |
| --- | --- |
| I01 | Бот и веб-приложение обмениваются данными через общую БД или API; источник данных единый. |
| I02 | Заявитель получает сообщения в чат об изменении статуса, например о принятии в работу и выполнении. |
| I03 | Отправка уведомления происходит не позднее одной минуты после изменения статуса. |

При этом раздел 4 требует показать уведомление заявителя в живой демонстрации. Для проекта принято включить I01–I03 в целевой объём реализации. Лимит доставки проверяется при доступности Telegram API; внешние сбои и повторные попытки отражаются отдельно.

## Результаты сдачи

| Код | Результат и критерий приёмки |
| --- | --- |
| D01 | Рабочий бот принимает заявки по трём группам классификатора, всего не менее девяти элементов. |
| D02 | Рабочее веб-приложение выполняет все операции: взять, назначить, переназначить, закрыть. |
| D03 | Живой полный цикл: заявка через бота → обработка через веб-приложение → уведомление заявителя. |
| D04 | Описание архитектуры со схемой взаимодействия бота, веб-приложения и БД. |
| D05 | Инструкция для нового оператора. |
| D06 | Расчёт производительности: сколько заявок в час выдерживает система. Минимальное требуемое число в исходном ТЗ не задано. |

## Технические ограничения

| Код | Ограничение |
| --- | --- |
| T01 | Стек выбирает команда. Серверная часть и БД размещаются локально на ноутбуке команды либо в бесплатной облачной среде. |
| T02 | Допускаются Python с aiogram, Flask/FastAPI, Django или аналогичные инструменты. |
| T03 | Готовые тикет-системы в качестве решения запрещены; открытые библиотеки и инструменты разработки разрешены. |

## Решения проекта и открытые вопросы

Выбраны Telegram и сценарий обслуживания учебного заведения с классификатором из примера. Конкретный стек ещё не реализован; предложение приведено в `PROMPT.md` и может быть изменено с обоснованием.

Исходное ТЗ не определяет способ входа сотрудников, подробную матрицу прав, трактовку фильтра по дате, правила повторного открытия и работу с отключёнными сотрудниками. Перед реализацией эти правила нужно описать как проектные решения, сохранив обязательные сценарии. Защита доступа к чужим заявкам, атомарная история, обработка конкурентных изменений и повторные попытки уведомлений — дополнения проекта, а не цитаты из ТЗ.

Статус на момент подготовки материалов: требований к реализованному приложению пока не проверяли; в репозитории подготовлены документы и структура.
